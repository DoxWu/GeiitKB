## 1. 分级标准

### 1.1 严重级别定义

| 级别 | 定义 | 处理时限 | 示例 |
|------|------|----------|------|
| **Critical** | 系统无法启动、数据丢失、安全漏洞、核心数据泄露 | 立即修复，阻塞上线 | 数据库连接失败、认证绕过、SQL 注入 |
| **High** | 核心功能不可用、影响主业务流程、无自动降级 | 优先处理，当日修复 | RAG 检索失败、用户无法登录、文档上传失败 |
| **Medium** | 辅助功能异常、有自动 workaround、不影响核心链路 | 建议处理，本周修复 | 监控采集失败、非关键 API 报错、日志缺失 |
| **Low** | 性能优化、弃用警告、环境适配、非功能性问题 | 可选处理，下个迭代 | 镜像过大、弃用 API 警告、端口冲突 |

### 1.2 分级决策流程

```
发现问题
  ├── 是否阻塞系统启动或存在安全漏洞？ → 是 → Critical
  ├── 否 → 是否影响核心业务功能（认证/检索/文档/问答）？ → 是 → High
  ├── 否 → 是否有自动降级/workaround 不影响主流程？ → 是 → Medium
  └── 否 → 是否为性能/优化/环境/警告类问题？ → 是 → Low
```

### 1.3 处理顺序

```
Critical → High → Medium → Low
```

## 3. P-01：Embedding 服务 404（High）

### 3.1 问题描述

| 项目 | 内容 |
|------|------|
| **严重级别** | High |
| **问题类型** | 配置缺陷 |
| **影响范围** | RAG 文档向量化全链路 |
| **阻塞部署** | 是（影响核心功能） |

### 3.2 现象

```
HTTP Request: POST https://api.deepseek.com/embeddings "HTTP/1.1 404 Not Found"
[embedding:primary] 健康探测 失败 (4029ms)
```

### 3.3 根因分析

- `.env` 中 `OPENAI_API_BASE=https://api.deepseek.com`（DeepSeek 仅提供 `/chat/completions`，不提供 `/embeddings` 端点）
- `EMBEDDING_MODEL_NAME="text-embedding-v4"`（此为阿里云模型名，非 DeepSeek 模型）
- `providers.yaml` 中 embedding primary 直接复用 `OPENAI_API_BASE`，导致请求发往 DeepSeek 的不存在的 `/embeddings` 端点

### 3.4 修复方案

在 [providers.yaml](file:///c:/Users/DOXIA/Desktop/企业知识库问答系统/kb_qa_system/backend/app/core/model_provider/providers.yaml) 的 embedding 区段新增 `cloud_fallback` 端点，复用阿里云降级 API：

```yaml
# 新增的云端降级 embedding 端点
- name: "cloud_fallback"
  type: openai
  model: "${EMBEDDING_FALLBACK_MODEL_NAME:${EMBEDDING_MODEL_NAME:text-embedding-ada-002}}"
  api_key: "${EMBEDDING_FALLBACK_API_KEY:${LLM_FALLBACK_API_KEY:${OPENAI_API_KEY}}}"
  api_base: "${EMBEDDING_FALLBACK_API_BASE:${LLM_FALLBACK_API_BASE:${OPENAI_API_BASE}}}"
  dimension: "${EMBEDDING_DIMENSION:1536}"
  enabled: "${LLM_FALLBACK_ENABLED:true}"
  health_check:
    enabled: true
    interval: 60
    timeout: 10
  tags: ["fallback", "cloud"]
```

### 3.5 降级链路（修复后）

```
Embedding 请求
  ├── primary（DeepSeek）→ 404 → 熔断器打开
  ├── cloud_fallback（阿里云）→ 200 ✅ → 返回向量
  └── local_fallback（HuggingFace）→ 最终兜底
```

### 3.6 设计亮点

- **零配置兼容**：新增的 `EMBEDDING_FALLBACK_*` 环境变量不设置时，自动降级到 `LLM_FALLBACK_*`，再降级到 `OPENAI_API_*`
- **嵌套占位符**：`${EMBEDDING_FALLBACK_API_KEY:${LLM_FALLBACK_API_KEY:${OPENAI_API_KEY}}}` 实现三级回退
- **维度一致**：cloud_fallback 和 primary 都使用 `EMBEDDING_DIMENSION`，避免向量维度不匹配

### 3.7 修复结果

✅ **已修复**。providers.yaml 加载验证通过，3 个 embedding 端点结构正确。

## 4. P-02：/metrics 端点 422（Medium）

### 4.1 问题描述

| 项目 | 内容 |
|------|------|
| **严重级别** | Medium |
| **问题类型** | 代码 Bug |
| **影响范围** | Prometheus 监控指标采集 |
| **阻塞部署** | 否（监控可选） |

### 4.2 现象

```
GET /metrics → 422 VALIDATION_ERROR
{"details": [{"loc": ["query", "args"], "msg": "Field required"}, ...]}
```

### 4.3 根因分析

- 文件：[metrics.py L99-L102](file:///c:/Users/DOXIA/Desktop/企业知识库问答系统/kb_qa_system/backend/app/api/routes/metrics.py#L99-L102)
- 原代码：
  ```python
  credentials: Optional[HTTPBasicCredentials] = Depends(
      _security if settings.PROMETHEUS_AUTH_ENABLED else None
  )
  ```
- 当 `PROMETHEUS_AUTH_ENABLED=False` 时，`Depends(None)` 导致 FastAPI 将 `None` 作为依赖项
- FastAPI 尝试从查询参数中获取 `args` 和 `kwargs`，返回 422 验证错误

### 4.4 修复方案

改为始终使用 `Depends(_security)`，在函数内部按开关判断是否验证：

```python
async def metrics(
    credentials: Optional[HTTPBasicCredentials] = Depends(_security),
):
    # Prometheus 未启用 → 404
    if not is_prometheus_enabled():
        raise HTTPException(status_code=404, ...)

    # 仅在启用认证时验证
    if settings.PROMETHEUS_AUTH_ENABLED:
        if credentials is None:
            raise HTTPException(status_code=401, ...)
        _verify_auth(credentials)

    # 返回指标数据
    data, content_type = get_metrics_data()
    return PlainTextResponse(content=data, media_type=content_type)
```

### 4.5 修复结果

✅ **已修复**。`Depends(_security)` 始终解析 Authorization 头（缺失时 credentials 为 None），函数内部按 `PROMETHEUS_AUTH_ENABLED` 开关决定是否验证。

## 6. P-05：镜像过大 18.7GB（Low）

### 6.1 问题描述

| 项目 | 内容 |
|------|------|
| **严重级别** | Low |
| **问题类型** | 性能优化 |
| **影响范围** | 构建速度、磁盘占用 |
| **阻塞部署** | 否 |

### 6.2 现象

后端镜像 18.7GB，远超合理范围（2-4GB）。

### 6.3 根因分析

通过 `docker history` 分析：

| 层 | 大小 | 原因 |
|----|------|------|
| `COPY --from=builder /opt/venv /opt/venv` | 5.96GB | PyTorch + opencv + langchain 等重依赖 |
| `RUN chown -R kbapp:kbapp /app /opt/venv` | 5.97GB | chown 复制了整个 venv 到新层 |

### 6.4 修复方案

在 [Dockerfile](file:///c:/Users/DOXIA/Desktop/企业知识库问答系统/kb_qa_system/backend/Dockerfile#L93-L111) 中：

1. 在 COPY 之前创建非 root 用户
2. 使用 `COPY --chown=kbapp:kbapp` 直接设置属主
3. 消除 `chown -R` 层（节省约 6GB）

```dockerfile
# 修复前：
COPY --from=builder /opt/venv /opt/venv
COPY . /app/
RUN chmod +x /app/entrypoint.sh && \
    groupadd -r kbapp && useradd -r -g kbapp ... && \
    chown -R kbapp:kbapp /app /opt/venv   # ← 此层 5.97GB

# 修复后：
RUN groupadd -r kbapp && useradd -r -g kbapp ...
COPY --chown=kbapp:kbapp --from=builder /opt/venv /opt/venv
COPY --chown=kbapp:kbapp . /app/
RUN chmod +x /app/entrypoint.sh            # ← 仅修改 entrypoint.sh 权限位
```

### 6.5 预期效果

| 指标 | 修复前 | 修复后（预期） |
|------|--------|----------------|
| 镜像大小 | 18.7GB | ~12.7GB（-32%） |
| chown 层 | 5.97GB | 0B（消除） |
| 构建时间 | 较长 | 缩短（少一层文件复制） |

> **注意**：实际瘦身效果需在下次 `docker build` 后验证。剩余 ~12GB 主要来自 PyTorch（sentence-transformers 依赖），可后续通过 CPU-only PyTorch 进一步优化。

### 6.6 修复结果

✅ **已修复**（Dockerfile 已优化）。镜像构建验证需在下次 `docker build` 时确认。

## 7. P-03：端口 5432 冲突（Low）

### 7.1 问题描述

| 项目 | 内容 |
|------|------|
| **严重级别** | Low |
| **问题类型** | 环境冲突 |
| **影响范围** | 本地 Docker 部署 |
| **阻塞部署** | 否（可绕过） |

### 7.2 现象

宿主机已有 PostgreSQL 服务（PID 7904）占用 5432 端口，Docker 容器无法绑定。

### 7.3 处理方式

此为环境问题，非代码缺陷。提供以下 workaround：

**方案 A（推荐）**：修改端口映射
```yaml
# docker-compose.override.yml（不入版本控制）
services:
  postgres:
    ports:
      - "5433:5432"  # 宿主机用 5433，容器间仍用 postgres:5432
```

**方案 B**：停止宿主机 PostgreSQL 服务

**方案 C**：不暴露端口（仅容器间访问）

### 7.4 处理结果

📝 **已提供 workaround**。验证期间使用方案 A 临时创建 `docker-compose.override.yml`，验证完成后已删除。
