## 1. 问题描述

| 项目 | 内容 |
|------|------|
| **问题类型** | 认证失败（401 Unauthorized） |
| **影响范围** | 所有通过前端登录页面的用户（包括管理员） |
| **严重级别** | High（核心认证功能不可用） |
| **复现条件** | 使用邮箱在前端登录页面登录，且账号的 username ≠ email |

### 1.1 现象

用户在前端登录页面输入邮箱和密码后，后端返回 401：

```json
{
  "error": {
    "code": "INVALID_CREDENTIALS",
    "message": "用户名或密码错误"
  },
  "remaining_attempts": 4
}
```

## 2. 调查过程

### 2.1 认证链路梳理

```
前端 LoginForm.tsx          后端 auth.py                数据库
     │                           │                        │
     ├─ 用户输入邮箱              │                        │
     ├─ { username: email } ──→  │                        │
     │                      ─→  credentials.username      │
     │                           ├─ User.username == email │ ← 查询条件
     │                           │              ↓          │
     │                           │     匹配失败 (None)     │
     │                           │              ↓          │
     │                    ←── 401 INVALID_CREDENTIALS      │
```

### 2.2 关键代码审查

#### 前端：LoginForm.tsx（L69-L71）

```tsx
// 后端使用 username 字段，将邮箱作为 username 传入
await login({ username: email, password });
```

前端登录表单收集的是**邮箱**（`<Input type="email" />`），但发送到后端时映射为 `username` 字段。

#### 后端：auth.py（原 L233）

```python
user = db.query(User).filter(User.username == username).first()
```

后端**仅按 `User.username` 字段查询**，不检查 `User.email`。

#### 管理员创建：create_superuser.py

```python
new_user = User(
    username=username,      # e.g., "admin"
    email=email,            # e.g., "admin@example.com"
    ...
    is_superuser=True,
)
```

管理员账号创建时，`username`（如 "admin"）和 `email`（如 "admin@example.com"）是**不同的值**。

### 2.3 数据流追踪

| 步骤 | 数据 | 位置 |
|------|------|------|
| 1. 用户在表单输入 | `email = "admin@example.com"` | LoginForm.tsx |
| 2. 前端构建请求体 | `{ username: "admin@example.com", password: "***" }` | LoginForm.tsx:70 |
| 3. 后端接收 | `credentials.username = "admin@example.com"` | auth.py:225 |

| 5. 查询结果 | `None`（数据库中 username="admin"） | - |
| 6. 密码验证 | bcrypt 验证失败（用户不存在） | auth.py:244 |
| 7. 返回 | `401 INVALID_CREDENTIALS` | auth.py:271 |

## 3. 根因分析

### 3.1 直接原因

前端与后端对 `username` 字段的语义理解不一致：

| 组件 | `username` 字段含义 |
|------|---------------------|
| 前端 LoginForm | 用户的邮箱地址 |
| 后端 auth.py | 数据库 `users.username` 列 |
| create_superuser.py | 独立的管理员用户名（如 "admin"） |

### 3.2 设计缺陷

前端登录表单使用邮箱作为登录标识（这是常见的 UX 实践），但后端登录端点仅支持按 `username` 查询，导致两者不匹配。

### 3.3 影响范围

- **管理员账号**：管理员通过 `create_superuser.py` 创建，`username` ≠ `email`，**必然 401**
- **注册用户**：通过 `/auth/register` 注册的用户，`username` ≠ `email`（用户名和邮箱是独立字段），**同样 401**
- **仅当 username = email 时**才能登录成功（极少见）

## 4. 修复方案

### 4.1 修复策略

**后端支持用户名或邮箱登录**（而非修改前端），理由：
1. 向后兼容：不破坏现有 API 契约
2. 用户体验提升：用户可用用户名或邮箱登录
3. 前端无需改动逻辑（仅更新注释）

### 4.2 后端修复

#### auth.py — 登录查询（L232-L238）

```python
# 修复前：
user = db.query(User).filter(User.username == username).first()

# 修复后：
user = db.query(User).filter(
    (User.username == username) | (User.email == username)
).first()
```

#### schemas/user.py — UserLogin schema（L156-L163）

```python
# 修复前：
username: str = Field(..., min_length=1, max_length=50, description="用户名")

# 修复后：
# max_length=100 对齐 User.email 字段长度，支持邮箱登录
username: str = Field(..., min_length=1, max_length=100, description="用户名或邮箱")
```

### 4.3 前端修复

#### LoginForm.tsx — 注释更新（L69-L70）

```tsx
// 修复前：
// 后端使用 username 字段，将邮箱作为 username 传入

// 修复后：
// 后端 username 字段同时支持用户名和邮箱
// 前端登录表单使用邮箱，将其作为 username 传入
```

## 7. 安全考量

### 7.1 时序攻击防护（保持有效）

修复后仍保持时序攻击防护：

```python
# 即使用户不存在也执行 bcrypt 验证（保持响应时间一致）
hashed_to_check = user.hashed_password if user else _DUMMY_HASH
password_ok = verify_password(credentials.password, hashed_to_check)
password_ok = password_ok and bool(user)
```

- 用户不存在时仍执行一次 bcrypt 验证（消耗相同时间）
- 攻击者无法通过响应时间判断用户名/邮箱是否存在

### 7.2 账号锁定机制（保持有效）

- `check_login_lock(username)` 仍以输入值作为锁键
- 连续失败达阈值后锁定（423）
- 限流：每分钟最多 5 次登录尝试

### 7.3 查询安全性

- 使用 SQLAlchemy ORM 的 `filter()` 方法，参数化查询防 SQL 注入
- `|` 运算符生成 `OR` SQL 条件，不影响查询安全性

### 7.4 已知限制

- 账号锁定以输入值（username 或 email）为键，同一账号的 username 和 email 会产生两个独立的锁计数器。这不是安全漏洞（路由级限流仍有效），但可在后续优化中统一为用户 ID 作为锁键。

## 8. 结论

### 8.1 根因

前端 LoginForm 将邮箱作为 `username` 字段发送，后端仅按 `User.username` 列查询，导致邮箱登录时查询不到用户，返回 401。

### 8.2 修复

后端登录查询改为 `(User.username == input) | (User.email == input)`，同时支持用户名和邮箱登录。
