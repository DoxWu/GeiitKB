## 一、简历版（直接用于简历）

### GeiIt企业知识库问答系统 ｜ 全栈开发 ｜ 2026.03 – 2026.07

**技术栈**：Python 3.11 / FastAPI / PostgreSQL+pgvector / Redis / Celery / React 18 + TypeScript / Vite / TailwindCSS / Docker / LangChain

**项目描述**：基于 RAG（检索增强生成）架构的企业级知识库问答系统，支持多格式文档上传、智能分块、向量+关键词混合检索、流式问答，具备完整的用户认证、权限控制、文档管理与运维监控体系，达到生产级部署标准。

**核心工作**：

- **RAG 混合检索引擎**：基于 pgvector 向量检索 + PostgreSQL 全文检索构建双路召回，引入 query 意图分类器实现动态权重调整；针对中文关键词检索失效问题，设计 2-gram bigram 滑窗分词 + ILIKE 模糊匹配策略，检索结果从 0 条恢复至 5 条，混合检索得分提升 15.5%
- **文档处理流水线**：使用 Celery 构建异步处理管线，支持 PDF/DOCX/MD/TXT 多格式解析、OCR 图片识别、多模态图片理解（Vision LLM 生成描述参与检索），通过 Redis 分布式锁（UUID + Lua CAS）防止并发重处理
- **LLM 服务可靠性**：实现熔断器模式（Redis 跨容器状态共享）+ 多 API Fallback（DeepSeek 推理 + 阿里云通义嵌入降级），保障 LLM 服务可用性；采用 SSE 流式响应 + 首字超时保护
- **安全防护**：实现 SSRF 防护（协议/IP/端口黑名单 + 流式限速）、XSS 防护（html.escape + MIME 构造防 CRLF 注入）、文件上传安全（MIME 双重校验 + 哈希去重 + 路径遍历防御）、文档级权限隔离
- **前端工程化**：React.lazy 代码分割 + Zustand 状态管理，实现文档多选批量操作、流式 Markdown 渲染（代码高亮 + KaTeX 公式）、HTTP 状态码分类的错误提示友好化
- **容器化部署**：Docker Compose 编排 5 个服务（api/worker/postgres/redis/flower），Alembic 自动迁移、非 root 用户运行、容器资源限制

### 八大功能模块

#### 1. 认证与用户管理
- 用户名/邮箱双模式登录 + JWT（Access 15min + Refresh 7天）
- 注册审批流：邮箱双次输入校验 → 管理员审批 → 密码设置链接（256位熵 Token，SHA-256 哈希存储，一次性，24h过期，限流5次/小时）
- 游客临时登录：Redis 计数器限制 20 次提问，禁止上传文档
- Token 黑名单（Redis）实现登出失效

#### 2. 文档管理
- 文档上传（拖拽 + 进度条 + 取消）+ URL 导入（SSRF 防护 + 流式下载限速）
- 文档列表：分页 + 筛选 + 排序（白名单映射防 SQL 注入）+ 游标分页
- 文档预览：文本类（`<pre>` 渲染）、PDF（iframe 内联）、DOCX（python-docx 提取文本）
- 文档库分支 CRUD + 未分类默认分支（folder_id=0 哨兵值）
- 多选批量操作（批量删除/批量移动，逐项权限校验，1-100条/批）
- 软删除（先 commit DB 再删向量，保证一致性优先）

#### 3. 文档处理流水线（Celery 异步）
- 多格式解析：PDF（pdfplumber 逐页提取）、DOCX（python-docx 段落+表格）、MD/TXT
- OCR 图片识别（Tesseract，检测扫描件 → 渲染图片 → 识别文字）
- 多模态图片理解（Vision LLM 生成图片描述作为独立 chunk 参与检索）
- 智能分块（chunk_size=800, overlap=150）+ 向量嵌入（1536 维）
- 文档重处理：分布式锁（Redis UUID + Lua CAS）防并发，持锁期间设 processing 关闭 TOCTOU 窗口

#### 4. 对话问答
- SSE 流式响应（首字超时保护，推理模型 30s 超时）
- 上下文管理：多轮对话历史 + token 截断
- 引用溯源：展示检索来源文档、分块、相似度、置信度标签
- 降级策略：LLM 不可用时返回检索结果 + fallback 消息

#### 5. 检索系统（核心）
- **向量检索**：pgvector + IVFFLAT 索引（probes=50），余弦相似度
- **关键词检索**：英文 `to_tsquery` + `ts_rank` 精确匹配；中文 2-gram bigram 滑窗分词 + `ILIKE` 模糊匹配（通配符转义防注入）
- **混合检索**：加权融合（vector_score × α + keyword_score × β），α/β 由 query 意图分类器动态调整
- **意图分类器复用**：复用 intent_classifier 组件实现动态权重，避免额外模型开销
- 检索结果：final_score 从 0.4713 提升至 0.5442（+15.5%）

#### 6. 权限与安全
- 文档访问控制：用户只能访问授权公共文档库 + 个人文档库，模型检索范围同步限制
- SSRF 防护：协议白名单 + IP 黑名单 + 端口黑名单 + 流式下载限速
- XSS 防护：`html.escape()` 转义用户输入 + `EmailMessage` 构造防 CRLF 注入
- 文件上传安全：MIME 双重校验（防伪造扩展名）+ SHA-256 哈希去重 + 路径遍历防御
- 恶意请求防护：用户 ID 不可篡改（从 JWT 提取，非客户端传入）

#### 7. 运维与监控
- 熔断器模式：API 健康探测（首字超时 + 错误率）→ 自动熔断 → Redis 跨容器状态共享 → 半开探测恢复

### 技术亮点与难点攻克

#### 1. 中文关键词检索失效修复
- **问题**：`query.strip().split()` 对中文无效（无空格分词），`to_tsquery('simple', '辅助系统功能设计')` 将整个中文字符串作为单个 token → 0 结果
- **方案**：双路匹配策略——英文词用 `to_tsquery` + `ts_rank` 精确匹配，中文用 2-gram bigram 滑窗分词 + `ILIKE %term%` OR 模糊匹配 + 按命中数量计分
- **成果**：关键词检索从 0 结果恢复到 5 结果，混合检索 final_score 提升 15.5%

#### 2. 流式响应 Session 失效陷阱
- **问题**：FastAPI `StreamingResponse` + `Depends(get_db)` 的请求级 session 在流式生成器后处理阶段（保存消息/记录埋点/生成摘要）已失效，导致 ORM 对象脱离 session
- **方案**：在 `event_stream()` 内部创建独立 `SessionLocal()` 进行后处理 DB 操作，流式生成器前捕获纯值（conv_id, user_id_val）避免依赖 ORM 对象

#### 3. 熔断器误开问题
- **问题**：推理模型（deepseek-v4-pro）首字延迟 10-30s，`LLM_STREAM_FIRST_TOKEN_TIMEOUT=5` 导致健康探测超时 → 熔断器打开 → 所有 LLM 调用被拦截
- **方案**：超时调至 30s + 清除 Redis 熔断器状态键（`circuit_breaker:*:open` / `circuit_breaker:*:fails`）

#### 4. Docker 非 root 用户卷权限
- **问题**：`.dockerignore` 排除 `uploads/`，镜像中无此目录，Docker 命名卷挂载时创建 `root:root 755` 空目录，非 root 用户（kbapp, uid=999）无法写入 → HTTP 500
- **方案**：Dockerfile `USER` 指令前显式 `mkdir -p /app/uploads && chown -R kbapp:kbapp /app/uploads`，重建镜像后删除旧命名卷

#### 5. 多 API Fallback 链路
- **问题**：DeepSeek 不支持 `/embeddings` 端点，嵌入请求需 fallback 到阿里云，但手动配置 API Key 时漏字符导致 401
- **方案**：`providers.yaml` 配置 `cloud_fallback` provider + 嵌套占位符语法，嵌入 fallback 显式指向阿里云，逐字符比对 API Key

## 三、面试常见问题准备

### Q1: 为什么选择 pgvector 而不是专用向量数据库（Milvus/Pinecone）？
**A**: pgvector 是 PostgreSQL 扩展，与业务数据共库，支持 SQL JOIN 检索结果与文档元数据联合查询，避免了向量库 + 关系库的数据一致性问题。IVFFLAT 索引在百万级向量下性能足够，且运维复杂度远低于独立向量库。对于企业知识库场景，文档量通常在万级，pgvector 是性价比最优的选择。

### Q2: 混合检索的动态权重是如何实现的？
**A**: 复用了已有的 query 意图分类器（intent_classifier），它原本用于判断用户查询是"事实型/列表型/描述型"等。我在此基础上新增 `QuerySubType` 枚举，根据查询子类型动态设置向量检索权重 α 和关键词检索权重 β。例如事实型查询（"系统支持哪些文件格式"）提高关键词权重，描述型查询（"辅助系统功能设计"）提高向量权重。这样无需引入额外模型，复用现有组件即可。

### Q3: 熔断器为什么用 Redis 而不是内存状态？
**A**: 因为 api 和 worker 是不同容器，LLM 调用可能从任一容器发起。如果熔断器状态只存内存，api 容器探测到 LLM 不可用后打开熔断器，但 worker 容器不知道，仍会继续调用。用 Redis 共享熔断器状态后，任一容器的健康检查失败会打开共享熔断器，所有容器都会跳过该端点，直到半开探测恢复。

### Q4: 流式响应中如何避免 Session 失效？
**A**: FastAPI 的 `Depends(get_db)` 提供的是请求级 Session，在 `StreamingResponse` 的生成器结束后（yield 后的清理代码），Session 可能已被关闭。我的方案是：在生成器内部创建独立的 `SessionLocal()` 进行后处理（保存消息、记录埋点、生成摘要），并在进入流式生成器前捕获所有需要的纯值（如 conv_id、user_id_val），避免依赖 ORM 对象的生命周期。

### Q5: 中文关键词检索为什么用 2-gram 而不是 jieba 分词？
**A**: 两个原因：1）jieba 需要额外依赖和词典维护，而 2-gram 是纯算法实现，无外部依赖；2）2-gram 对专业术语和未登录词（OOV）更友好——jieba 可能将"辅助系统功能设计"错误切分，而 2-gram 的"辅助/助系/系统/统功/功能/能设/设计"滑窗能确保至少部分匹配。配合 ILIKE 模糊匹配，召回率更高。这是我借鉴了 `intent_service._extract_keywords` 的 bigram 分词思路。
