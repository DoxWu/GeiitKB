### 1.2 当前权重策略的问题

**静态权重（0.7/0.3）对所有查询一视同仁**，无法适配不同类型的问题：

| 问题类型 | 示例 | 理想权重 | 当前权重效果 |
|----------|------|----------|-------------|
| 精确匹配型 | "asyncio.gather 报错 RuntimeError" | 关键词 0.6+ | 关键词权重不足，可能漏召 |
| 语义理解型 | "如何实现异步并发" | 向量 0.9+ | 当前 0.7 尚可，但非最优 |
| 定义解释型 | "什么是事件循环" | 均衡 0.5/0.5 | 固定权重可能偏向一方 |
| 代码调试型 | "except ValueError 怎么写" | 关键词 0.5+ | 代码标识符需精确匹配 |

### 1.3 现有可复用基础设施

- **意图分类器** [intent_classifier.py](file:///c:/Users/DOXIA/Desktop/企业知识库问答系统/kb_qa_system/backend/app/services/intent_classifier.py)：已实现规则预判 + LLM 分类双重策略，识别 KB_QUERY/CHITCHAT/FOLLOWUP/META 四类意图

  - LLM 层：规则无法判断时调用 LLM，约 200ms 延迟
- **Reranker 重排序**：`reranker_service` 已集成 cross-encoder 重排序（`ENABLE_RERANKING=True` 时启用），对候选结果二次打分

### 1.4 关键词检索实现

当前关键词检索使用 PostgreSQL 全文检索（非独立 BM25 引擎）：


## 二、轻量模型预处理方案

### 2.1 方案 A：基于规则的关键词特征提取

**核心思路**：在检索前用纯 Python 规则分析问题特征，映射到权重。

**实现方式**：

```python
def analyze_query_features(question: str) -> float:
    """
    分析问题特征，返回关键词检索权重（0.0-1.0）

    规则映射：
    - 含错误码（如 RuntimeError, EACCES）→ keyword_weight=0.6
    - 含代码标识符（如 asyncio.gather, np.array）→ keyword_weight=0.5
    - 含数字/版本号（如 Python 3.12, HTTP 404）→ keyword_weight=0.5
    - 含引号包裹的精确短语 → keyword_weight=0.7
    - 纯语义问题（如何/为什么/什么是）→ keyword_weight=0.2
    - 默认 → keyword_weight=0.3（与当前静态值一致）
    """
    import re
    # 错误码模式：大驼峰 + Error/Exception
    if re.search(r'\b[A-Z][a-z]+[A-Z]?Error\b|\b[A-Z]+Exception\b', question):
        return 0.6
    # 代码标识符：模块.方法 或 方法()
    if re.search(r'\b[a-z_]+\.[a-z_]+\b', question):
        return 0.5
    # 版本号/HTTP状态码
    if re.search(r'\b\d+\.\d+\b|\bHTTP \d{3}\b', question):
        return 0.5
    # 语义类问题
    if re.search(r'^(如何|为什么|什么是|怎么|怎样)', question):
        return 0.2
    return 0.3  # 默认
```

**优势**：
- 成本极低（~4h 工时），纯 Python，无额外依赖
- 零延迟（微秒级正则匹配）
- 规则透明，易于调试和调整

**劣势**：
- 规则覆盖面有限，边界 case 难以穷举
- 无法理解语义，"怎么解决 RuntimeError" 会被识别为语义类（权重 0.2），但实际需要精确匹配错误码
- 维护成本随规则增加而上升

### 2.2 方案 B：复用现有 intent_classifier（⭐ 推荐）

**核心思路**：扩展 `intent_classifier.py`，在 KB_QUERY 意图内细分"精确匹配型"vs"语义理解型"，映射到不同权重。

**实现方式**：

1. **扩展 IntentType 枚举**（或新增子类型字段）：

```python
# 在 IntentType.KB_QUERY 基础上细分
class QuerySubType(str, Enum):
    """KB_QUERY 子类型（用于动态权重分配）"""
    EXACT_MATCH = "exact_match"      # 精确匹配型：错误码、API名、代码片段
    SEMANTIC = "semantic"            # 语义理解型：概念解释、方法推荐
    HYBRID = "hybrid"                # 混合型：无法明确判定，用默认权重
```

2. **规则预判扩展**（零延迟）：

```python
# intent_classifier.py 新增精确匹配检测规则
_EXACT_MATCH_PATTERNS = [
    re.compile(r'\b[A-Z][a-z]+Error\b'),           # 错误类型
    re.compile(r'\b[A-Z]+Exception\b'),
    re.compile(r'\b[a-z_]+\.[a-z_]+\('),           # 模块.方法()
    re.compile(r'\bHTTP \d{3}\b'),                 # HTTP 状态码
    re.compile(r'`[^`]+`'),                        # 反引号包裹的代码
]

def _detect_query_sub_type(self, query: str) -> QuerySubType:
    """检测 KB_QUERY 子类型（规则预判，零延迟）"""
    for pattern in _EXACT_MATCH_PATTERNS:
        if pattern.search(query):
            return QuerySubType.EXACT_MATCH
    # 语义类问题特征
    if re.search(r'^(如何|为什么|什么是|怎么|怎样|区别|对比)', query):
        return QuerySubType.SEMANTIC
    return QuerySubType.HYBRID
```

3. **意图 → 权重映射表**：

```python
# 权重映射配置（可放入 config.py）
QUERY_SUBTYPE_WEIGHTS = {
    QuerySubType.EXACT_MATCH: 0.6,   # 关键词权重↑
    QuerySubType.SEMANTIC: 0.2,      # 向量权重↑
    QuerySubType.HYBRID: 0.3,        # 默认均衡
}
```

4. **权重透传**：`rag_chain.py` → `vector_store.search(keyword_weight=dynamic_weight)`

```python
# rag_chain.py retrieve_context 中
from app.services.intent_classifier import intent_classifier
sub_type = intent_classifier._detect_query_sub_type(query)
dynamic_keyword_weight = QUERY_SUBTYPE_WEIGHTS.get(sub_type, 0.3)

results = vector_store.search(
    query,
    top_k=search_k,
    document_ids=accessible_ids,
    keyword_weight=dynamic_keyword_weight,  # 新增参数
)
```

5. **vector_store.search() 签名扩展**：

```python
def search(
    self,
    query: str,
    top_k: Optional[int] = None,
    document_ids: Optional[List[int]] = None,
    enable_hybrid: Optional[bool] = None,
    keyword_weight: Optional[float] = None,  # 新增：动态权重
) -> List[Dict[str, Any]]:
    ...
    # 使用动态权重覆盖配置默认值
    if keyword_weight is None:
        keyword_weight = settings.KEYWORD_SEARCH_WEIGHT
    vector_weight = 1 - keyword_weight
```

**优势**：
- 复用现有 `intent_classifier` 基础设施，与架构一致
- 规则预判零延迟，LLM 分类仅在规则无法判断时触发
- 权重映射表可配置，易于调优
- 成本适中（~6h 工时）

**劣势**：
- LLM 分类增加 ~200ms 延迟（但规则预判命中时无延迟）
- 需要扩展 intent_classifier 的接口，有一定改动范围

### 2.3 方案 C：轻量 Embedding 相似度分析

**核心思路**：预定义"定义类"/"检索类"/"精确匹配类"模板向量，计算问题与模板的余弦相似度，插值权重。

**实现方式**：

```python
# 预定义模板问题及其理想权重
WEIGHT_TEMPLATES = [
    {"question": "asyncio.gather 报错 RuntimeError 怎么解决", "keyword_weight": 0.6},
    {"question": "如何实现异步并发编程", "keyword_weight": 0.2},
    {"question": "什么是事件循环", "keyword_weight": 0.4},
    {"question": "Python 读取文件的方法", "keyword_weight": 0.3},
    # ... 更多模板
]

def compute_dynamic_weight(question: str) -> float:
    """基于 Embedding 相似度计算动态权重"""
    question_embedding = embedding_service.embed(question)
    weighted_sum = 0.0
    similarity_sum = 0.0
    for template in WEIGHT_TEMPLATES:
        template_embedding = template["_embedding"]  # 预计算缓存
        similarity = cosine_similarity(question_embedding, template_embedding)
        weighted_sum += similarity * template["keyword_weight"]
        similarity_sum += similarity
    if similarity_sum == 0:
        return 0.3  # 默认
    return weighted_sum / similarity_sum  # 加权平均
```

**优势**：
- 理解语义，不依赖硬编码规则
- 权重连续平滑，避免离散跳变
- 可通过增减模板灵活调整

**劣势**：
- 每次检索需额外一次 Embedding 调用（+100ms 延迟 + API 成本）
- 模板设计需调优，数量太少不准确，太多影响性能
- 成本最高（~8h 工时）
- Embedding 服务不可用时需降级（fallback 到默认权重）

## 三、动态权重分配机制实现成本

### 3.1 改动范围对比

| 改动项 | 方案 A | 方案 B | 方案 C |
|--------|--------|--------|--------|
| `vector_store.py` | search() 新增 keyword_weight 参数 | 同 A | 同 A |
| `rag_chain.py` | retrieve_context 新增特征分析 | retrieve_context 新增子类型检测 | retrieve_context 新增 Embedding 相似度计算 |
| `intent_classifier.py` | 不改 | 新增 _detect_query_sub_type + 权重映射 | 不改 |
| `config.py` | 不改 | 新增 QUERY_SUBTYPE_WEIGHTS 配置 | 不改 |
| 新增模块 | query_analyzer.py（可选） | 无（扩展现有） | weight_templates.py |
| 工时预估 | ~4h | ~6h | ~8h |

### 3.2 延迟影响

| 方案 | 额外延迟 | 触发条件 |
|------|----------|----------|
| 方案 A | <1ms（正则匹配） | 每次检索 |
| 方案 B | <1ms（规则命中）/ ~200ms（LLM 分类） | 规则未命中时触发 LLM |
| 方案 C | ~100ms（Embedding API 调用） | 每次检索 |

### 3.3 风险评估

| 风险 | 方案 A | 方案 B | 方案 C |
|------|--------|--------|--------|
| 权重抖动（相同问题不同权重） | 低（规则确定性） | 中（LLM 可能不一致） | 低（Embedding 确定性） |
| 检索延迟增加 | 可忽略 | 规则路径可忽略，LLM 路径 +200ms | +100ms（显著） |
| 调试复杂度 | 低（规则透明） | 中（需追踪分类结果） | 高（Embedding 黑盒） |
| 维护成本 | 中（规则需维护） | 低（映射表可配置） | 中（模板需调优） |
| 降级容错 | 默认权重 0.3 | 降级为 KB_QUERY 默认权重 | Embedding 不可用时降级为默认 |

## 四、预期影响及潜在收益

### 4.1 检索效果预期

基于行业经验和系统当前查询分布的估算：

| 问题类型 | 占比（估） | 当前准确率 | 动态权重后准确率 | 提升 |
|----------|-----------|-----------|-----------------|------|
| 精确匹配型 | 30% | 65% | 80% | +15% |
| 语义理解型 | 40% | 75% | 78% | +3% |
| 混合型 | 30% | 70% | 72% | +2% |
| **整体** | 100% | 70% | 76% | **+6%** |

**关键收益**：
- 精确匹配类问题（错误码、API 名、代码片段）准确率提升最显著（+10-20%）
- 语义类问题略有提升（向量权重从 0.7 提升至 0.8 时，召回率改善）
- 整体检索准确率预期提升 5-15%

### 4.2 用户体验影响

- **正面**：精确匹配类问题能更快命中目标文档，减少"答非所问"
- **负面**：方案 B/C 的额外延迟可能影响首字响应时间（当前 LLM_STREAM_FIRST_TOKEN_TIMEOUT=30s，200ms 延迟在可接受范围内）

### 4.3 潜在风险

1. **权重抖动**：LLM 分类（方案 B）可能对相似问题给出不同分类，导致检索结果不一致
   - 缓解：规则预判优先，LLM 仅作兜底；对分类结果缓存（相同问题 5 分钟内复用）
2. **过度优化**：动态权重可能在某些 case 上反而降低效果
   - 缓解：实施 A/B 测试，对比静态权重和动态权重的检索质量指标
3. **调试难度**：动态权重使检索行为不可预测，排查"为什么没召回"更困难
   - 缓解：在日志中记录每次检索的权重分配原因（如 `keyword_weight=0.6, reason=exact_match_error_pattern`）

## 五、综合建议

### 5.1 推荐方案：B（复用 intent_classifier）

**理由**：
1. **架构一致性**：系统已有 intent_classifier 基础设施，扩展子类型分类自然融入现有架构
2. **成本适中**：6h 工时，改动范围可控
3. **延迟可控**：规则预判路径零延迟，仅规则未命中时触发 LLM（可缓存结果）
4. **可配置性**：权重映射表放入 config.py，无需改代码即可调优
5. **降级安全**：intent_classifier 已有完善的降级策略（LLM 不可用时降级为 KB_QUERY）

### 5.2 实施路径建议

1. **Phase 1**（2h）：扩展 `vector_store.search()` 支持 `keyword_weight` 可选参数
2. **Phase 2**（2h）：在 `intent_classifier.py` 新增 `_detect_query_sub_type()` 规则预判
3. **Phase 3**（1h）：在 `rag_chain.py` 透传动态权重
4. **Phase 4**（1h）：在 `config.py` 新增权重映射配置 + 日志记录
5. **Phase 5**：灰度 A/B 测试
   - 50% 流量用静态权重（0.3），50% 用动态权重
   - 对比指标：检索命中率、用户点赞率、首字延迟
   - 观察 1-2 周后决定是否全量启用

### 5.3 不推荐方案 C 的理由

- 每次检索额外 Embedding 调用（+100ms 延迟 + API 成本），性价比不高
- Embedding 服务不可用时需降级，增加了系统复杂度
- 模板设计需要大量领域知识调优，初始效果不确定

### 5.4 长期演进方向

如果方案 B 效果验证良好，可进一步考虑：
- **自适应权重**：基于用户反馈（点赞/点踩）自动调整权重映射表
- **问题聚类**：用 Embedding 对历史问题聚类，为每类问题学习最优权重
- **多阶段检索**：先粗召回（大 top_k + 均衡权重），再精排序（reranker + 动态权重）
