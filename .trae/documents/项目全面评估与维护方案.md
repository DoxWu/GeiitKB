## 第二章：改进点详细清单

### A. 功能完善（4 项）

#### E1-01 无 CI/CD 流水线

| 属性 | 值 |
|------|-----|
| **优先级** | P2 |
| **实施难度** | 中 |
| **预期效果** | 自动化测试/构建/部署，减少人工错误，提升交付效率 |

**问题描述**：项目没有 `.github/workflows/` 目录，缺少 GitHub Actions 或其他 CI/CD 配置。所有测试、构建、部署均需手动执行，容易遗漏且无法在 PR 阶段自动验证。

**涉及文件**：项目根目录（缺少 `.github/workflows/ci.yml`）

**实施建议**：
1. 创建 `.github/workflows/ci.yml`，包含以下 job：
   - **backend-test**：`cd kb_qa_system/backend && pip install -r requirements.txt && pytest`
   - **frontend-test**：`cd kb_qa_system/frontend && npm ci && npm run test`
   - **frontend-build**：`cd kb_qa_system/frontend && npm run build`
   - **lint**：`npm run lint` + `python -m ruff check`
2. 触发条件：push to main、pull request
3. 后续可扩展：自动部署到 Railway（Railway GitHub 集成或 webhook）

#### E1-02 D9-01 releaseCommand 缺失

| 属性 | 值 |
|------|-----|
| **优先级** | P1 |
| **实施难度** | 低 |
| **预期效果** | 解决多副本并发部署时的迁移冲突 |

**问题描述**：`backend/railway.json` 仅有 `healthcheckPath`，缺少 `"releaseCommand": "alembic upgrade head"`。当前 entrypoint.sh 在每个 API 副本启动时执行迁移，多副本并发部署时可能迁移冲突。这与项目规范（project_memory.md）中的"Railway must be configured with `releaseCommand = "alembic upgrade head"`"不符。

**涉及文件**：`kb_qa_system/backend/railway.json`

**实施建议**：
1. 在 `railway.json` 的 `deploy` 对象中添加：`"releaseCommand": "alembic upgrade head"`
2. 在 `entrypoint.sh` 中添加 `MIGRATE_ON_STARTUP` 环境变量检测：
   ```bash
   if [ "${MIGRATE_ON_STARTUP:-true}" = "true" ]; then
       run_migrations
   fi
   ```
3. Railway 部署时设 `MIGRATE_ON_STARTUP=false`（由 releaseCommand 执行迁移）
4. 非 Railway 部署保持 `MIGRATE_ON_STARTUP=true`（默认值）

#### E1-03 无 API 限流统一中间件

| 属性 | 值 |
|------|-----|
| **优先级** | P3 |
| **实施难度** | 中 |
| **预期效果** | 统一限流管理，降低维护成本 |

**问题描述**：当前限流配置分散在各路由端点中（注册申请 3次/小时、状态查询 10次/分钟、设置密码 5次/小时等），缺少统一的限流中间件，新增端点时容易遗漏限流配置。

**涉及文件**：`backend/app/core/rate_limit.py`、各路由文件

**实施建议**：
1. 创建 `backend/app/middleware/rate_limit_middleware.py`，支持基于路径模式的限流配置
2. 定义限流规则配置表（路径模式 → 限制次数/时间窗口）
3. 对未匹配规则的路径应用默认限流（如 60次/分钟）
4. 逐步迁移现有端点的限流到中间件模式

#### E1-04 无 WebSocket 实时通知

| 属性 | 值 |
|------|-----|
| **优先级** | P3 |
| **实施难度** | 高 |
| **预期效果** | 实时推送审批结果，提升用户体验 |

**问题描述**：注册审批完成后，用户需要手动刷新页面查看状态。缺少 WebSocket 实时推送机制，审批结果、文档处理完成等事件无法实时通知用户。

**涉及文件**：`backend/app/main.py`（WebSocket 端点）、前端通知组件

**实施建议**：
1. 后端：添加 WebSocket 端点 `/ws/notifications`，基于用户 JWT 认证
2. 后端：审批完成、文档处理完成等事件通过 Redis Pub/Sub 推送
3. 前端：创建 `useNotification` hook，连接 WebSocket 接收通知
4. 前端：收到通知后更新 store 状态并展示 Toast

#### E4-02 passlib==1.7.4 与 bcrypt 4.x 兼容性问题

| 属性 | 值 |
|------|-----|
| **优先级** | P2 |
| **实施难度** | 低 |

**涉及文件**：`backend/requirements.txt:45`

**实施建议**：
1. **方案 A（推荐）**：迁移到 `bcrypt` 库直接使用，移除 passlib 依赖
2. **方案 B**：在 requirements.txt 中固定 `bcrypt<4.0`（`bcrypt==3.2.2`）
3. **方案 C**：使用 passlib 的开发分支（不推荐，不稳定）
4. 迁移后运行全量测试验证密码哈希功能正常

#### E4-05 nginx 缺少部分安全头

| 属性 | 值 |
|------|-----|
| **优先级** | P2 |
| **实施难度** | 低 |
| **预期效果** | 完善安全头防护 |

**问题描述**：`nginx.conf` 已配置 CSP，但可能缺少 `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Strict-Transport-Security`、`Referrer-Policy` 等安全头。

**涉及文件**：`frontend/nginx.conf`

**实施建议**：
1. 添加以下安全头：
   ```nginx
   add_header X-Content-Type-Options "nosniff" always;
   add_header X-Frame-Options "DENY" always;
   add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
   add_header Referrer-Policy "strict-origin-when-cross-origin" always;
   add_header Permissions-Policy "camera=(), microphone=(), geolocation=()" always;
   ```
2. 使用 securityheaders.com 评估安全头完整性

## 第六章：版本迭代计划

### 6.1 版本号策略

采用 **Semantic Versioning**（语义化版本）：

```
MAJOR.MINOR.PATCH
  │     │     │
  │     │     └─ 向后兼容的 bug 修复
  │     └─ 向后兼容的新功能
  └─ 不兼容的 API/架构变更
```

当前版本：`0.x.0`（正式发布前），首个正式版本：`1.0.0`

### 6.2 发布周期

| 版本类型 | 周期 | 内容 |
|----------|------|------|
| Patch（0.0.x） | 每周（按需） | bug 修复、安全补丁 |
| Minor（0.x.0） | 每 2 周 | 新功能、体验优化 |
| Major（x.0.0） | 按需（不频繁） | 架构变更、不兼容更新 |

### 6.3 发布流程

```
1. 创建 release 分支（release/vX.Y.Z）
2. 在 release 分支上运行全量测试
3. 更新 CHANGELOG.md
4. 合并到 main 分支
5. 打 Git tag（vX.Y.Z）
6. Railway 自动部署（通过 GitHub 集成）
7. 灰度验证（参考 CANARY_RELEASE.md）
8. 全量发布
9. 发布后验证（健康检查 + 核心功能测试）
```

### 6.4 分支策略

| 分支 | 用途 | 命名规范 | 合并规则 |
|------|------|----------|----------|
| `main` | 生产分支 | - | 只接受 PR 合并 |
| `develop` | 开发分支 | - | 定期合并到 main |
| `feature/*` | 功能分支 | `feature/D1-01-folder-crud` | 合并到 develop |
| `fix/*` | 修复分支 | `fix/login-redirect-bug` | 合并到 develop |
| `release/*` | 发布分支 | `release/v1.2.0` | 合并到 main + develop |
| `hotfix/*` | 紧急修复 | `hotfix/security-patch` | 合并到 main + develop |

### 6.5 回滚策略

引用已有文档 `docs/ROLLBACK_SOP.md`：
1. **代码回滚**：Railway Dashboard → 选择上一个部署 → Redeploy
2. **数据库回滚**：`alembic downgrade -1`（需评估兼容性）
3. **回滚决策**：P0 事故立即回滚，P1 事故 30 分钟内无法修复则回滚

## 第七章：代码审查规范

### 7.1 审查流程

```
开发者提交 PR → CI 自动检查 → 人工审查 → 合并
     │              │              │           │
     │              │              │           └─ squash merge 到目标分支
     │              │              └─ 至少 1 人 Approve
     │              └─ 测试 + lint + build 全部通过
     └─ 填写 PR 描述（变更说明 + 测试方式）
```

### 7.2 审查清单

| 维度 | 检查项 |
|------|--------|
| **功能正确性** | 代码是否实现了预期功能？边界条件是否处理？错误路径是否覆盖？ |
| **安全性** | 是否有 SQL 注入/XSS/SSRF 风险？敏感信息是否泄露？权限校验是否完整？ |
| **性能** | 是否有 N+1 查询？是否有不必要的全表扫描？缓存使用是否合理？ |
| **测试** | 是否有对应的单元测试？测试是否验证行为而非 mock 调用？ |
| **代码规范** | 命名是否清晰？注释是否充分（中文）？是否有重复代码？ |
| **文档** | API 变更是否更新了文档？新功能是否更新了 CHANGELOG？ |

### 7.3 审查权限

| 变更类型 | 审查人数 | 审查人要求 |
|----------|----------|------------|
| 普通功能/修复 | 1 人 | 任何团队成员 |
| 核心路径（认证/权限/支付） | 2 人 | 至少 1 名核心维护者 |
| 架构变更 | 2 人 | 技术负责人 + 1 名核心维护者 |
| 紧急 hotfix | 1 人 | 核心维护者（事后补充审查） |

### 7.4 Commit Message 规范

采用 [Conventional Commits](https://www.conventionalcommits.org/)：

```
<type>(<scope>): <subject>
```

## 第八章：性能监控与技术债务管理

### 8.1 性能监控方案

#### 监控指标体系

| 类别 | 指标 | 来源 | 告警阈值 |
|------|------|------|----------|
| **API 性能** | http_request_duration_p95 | Prometheus | > 500ms (warning) |
| **API 错误率** | http_5xx_error_rate | Prometheus | > 5% (warning), > 10% (critical) |
| **RAG 链路** | rag_total_duration_p95 | Prometheus | > 30s (warning) |
| **检索性能** | rag_retrieval_duration_p95 | Prometheus | > 5s (warning) |
| **LLM 性能** | rag_llm_duration_p95 | Prometheus | > 20s (warning) |
| **Celery 任务** | task_queue_length | Flower | > 100 (warning) |
| **数据库** | db_connection_pool_usage | SQLAlchemy | > 80% (warning) |
| **Redis** | redis_memory_usage | Redis INFO | > 80% (warning) |
| **系统** | cpu_usage / memory_usage | Railway | > 80% (warning) |

#### Grafana 仪表盘

已有 Grafana 监控栈（`monitoring/docker-compose.monitoring.yml`），建议创建以下仪表盘：
1. **API 概览**：请求量、错误率、P95/P99 延迟、状态码分布
2. **RAG 链路**：检索耗时、LLM 耗时、降级次数、Token 消耗
3. **基础设施**：数据库连接池、Redis 内存、Celery 队列
4. **业务指标**：文档上传量、问答次数、活跃用户数

### 8.2 性能基线与 SLA 目标

| 指标 | 基线值 | SLA 目标 | 说明 |
|------|--------|----------|------|
| API P95 延迟 | < 200ms | < 500ms | 非 LLM 接口 |
| LLM P95 延迟 | < 15s | < 30s | RAG 问答接口 |
| 检索 P95 延迟 | < 2s | < 5s | 向量检索 |
| 可用性 | 99.9% | 99.5% | 月度可用率 |
| 错误率 | < 0.1% | < 1% | 5xx 错误率 |

### 8.3 技术债务分类

| 类别 | 定义 | 示例 | 偿还策略 |
|------|------|------|----------|
| **架构债务** | 设计不合理或过度耦合 | 限流分散配置（E1-03） | 重构为统一中间件 |
| **测试债务** | 测试覆盖不足或质量低 | 前端页面测试缺失（E3-01） | 每迭代补充 2-3 个测试 |
| **文档债务** | 文档缺失或过时 | 缺少根 README（E3-04） | 每迭代补充 1-2 个文档 |
| **依赖债务** | 依赖过时或有漏洞 | passlib 兼容性（E4-02） | 每月评估依赖更新 |
| **安全债务** | 安全加固不完整 | 缺少安全头（E4-05） | 每季度安全审计 |

### 8.4 技术债务跟踪

1. **Issue 标签**：使用 `tech-debt` 标签标记技术债务 issue
2. **分类标签**：`debt/architecture`、`debt/test`、`debt/docs`、`debt/dependency`、`debt/security`
3. **优先级标签**：`debt/high`、`debt/medium`、`debt/low`
4. **里程碑分配**：将高优先级技术债务分配到迭代里程碑
5. **看板管理**：在项目管理看板中维护"技术债务"列

### 8.5 技术债务偿还计划

**原则**：每个迭代分配 20% 的时间偿还技术债务。

| 迭代 | 偿还项 | 预估工时 |
|------|--------|----------|
| Sprint 1 | E1-02 releaseCommand + E4-02 passlib 修复 | 4h |
| Sprint 2 | E4-05 安全头 + E3-04 README | 4h |
| Sprint 3 | E1-01 CI/CD + E3-02 覆盖率阈值 | 8h |
| Sprint 4 | E3-01 前端页面测试（3 个页面） | 8h |
| Sprint 5 | E6-03 备份验证 + E6-04 Runbook | 8h |
| Sprint 6 | E3-01 前端页面测试（剩余页面） | 8h |

### 8.6 文档更新策略

| 文档类型 | 更新时机 | 负责人 | 审查人 |
|----------|----------|--------|--------|
| README.md | 新功能/架构变更 | PR 作者 | 审查者 |
| API 文档 | API 变更 | PR 作者 | 审查者 |

每月执行一次文档一致性检查：
1. 代码中的 API 路径与文档一致
2. 环境变量列表与 `.env.example` 一致
3. 部署步骤与实际流程一致
4. 文档间的交叉引用有效（无死链）
